# Глава 6. Тесты без железа

Драйвер написан, но проверить его на плате пока нельзя, потому что платы нет. Тесты решают эту задачу. Логика драйвера (какие байты отправлены, как разобраны полученные) не зависит от кристалла, и её можно проверить на обычном компьютере.

## Идея заглушки

Драйвер просит у пользователя "что-нибудь, что реализует `I2c`" ([глава 4](04-rust-minimum.md)). В тестах мы подсовываем ему не настоящую шину, а заглушку из крейта `embedded-hal-mock`. Заглушка получает заранее составленный сценарий. Он описывает, какие обращения драйвер должен сделать и что на них ответить.

Если драйвер сделает что-то не по сценарию, заглушка прервёт тест с описанием расхождения.

## Разбор одного теста

```rust
use embedded_hal_mock::eh1::i2c::{Mock as I2cMock, Transaction as T};
use lm75_guide::{Address, Lm75};

const ADDR: u8 = 0x48;
const TEMPERATURE: u8 = 0x00;

#[test]
fn raw_value_is_in_eighths() {
    let expectations = [T::write_read(ADDR, vec![TEMPERATURE], vec![0x19, 0x00])];
    let mut sensor = Lm75::new(I2cMock::new(&expectations), Address::default());

    assert_eq!(sensor.read_temperature_raw().unwrap(), 200);

    sensor.destroy().done();
}
```

Тест состоит из трёх частей.

**Сценарий.** Строка с `expectations` говорит следующее. Драйвер должен выполнить `write_read` по адресу `0x48`, записать один байт `0x00` и получить в ответ байты `0x19`, `0x00`. Это в точности то, что делает настоящий LM75, если в нём лежит 25 °C.

**Действие.** Драйвер создаётся с заглушкой вместо шины, и вызывается проверяемый метод. Ожидаемое значение 200 взято из таблицы в [главе 3](03-i2c-and-datasheet.md), а не вычислено повторением кода драйвера. Это важно: если вычислять ожидание той же формулой, что и в коде, тест не обнаружит ошибку в формуле.

**Завершение.** Метод `done()` проверяет, что сценарий выполнен до конца. Допустим, в сценарии два обращения, а драйвер сделал одно. Без `done()` такой тест пройдёт, а с ним завершится ошибкой.

Для вызова `done()` нужна сама заглушка, но она отдана драйверу. Поэтому тест сначала возвращает её методом `destroy()`, а затем вызывает `done()`. Это вторая причина, по которой `destroy` существует.

## Какие случаи покрыты

| Тест | Что проверяет |
|---|---|
| `address_from_pins` | Преобразование состояния выводов в адрес |
| `uses_configured_address` | Драйвер обращается по выбранному адресу, а не по умолчанию |
| `positive_temperature` | `0x1900` даёт +25,0 |
| `temperature_with_fraction` | `0x0020` даёт +0,125 |
| `negative_temperature` | `0xE700` даёт -25,0 |
| `range_limits` | Границы диапазона датчика, +125 и -55 |
| `unused_low_bits_are_ignored` | Мусор в пяти младших битах не влияет на результат |
| `raw_value_is_in_eighths` | Сырое значение измеряется в шагах по 0,125 |
| `shutdown_keeps_other_bits` | Установка бита не затрагивает остальные |
| `wake_keeps_other_bits` | Сброс бита не затрагивает остальные |
| `bus_error_is_passed_up` | Ошибка шины доходит до вызывающего |

Выбор случаев не случаен. Каждый из них защищает конкретную возможную ошибку. Граничные значения проверяют знаковую арифметику. Тест с мусором в младших битах проверяет, что сдвиг действительно выполняется. Тесты регистра конфигурации ловят ошибку "записал только свой бит и затёр остальные".

## Тест должен уметь падать

Зелёный тест сам по себе ничего не доказывает. Он может проходить, потому что проверяет не то. Надёжный способ убедиться в обратном - намеренно сломать код и посмотреть, что произойдёт.

Откройте `src/lib.rs` и замените строку

```rust
Ok(i16::from_be_bytes(buffer) >> 5)
```

на

```rust
Ok((u16::from_be_bytes(buffer) >> 5) as i16)
```

Это правдоподобная ошибка: число собрано как беззнаковое, а потом приведено к знаковому. Запустите `cargo test`. Упадут два теста (вывод ниже сокращён).

```
negative_temperature panicked: left: 231.0, right: -25.0
range_limits panicked:         left: 201.0, right: -55.0
```

Беззнаковый сдвиг заполнил старшие биты нулями, и вместо -25 получилось +231. Положительные температуры при этом проходят, и если бы в наборе не было отрицательных значений, ошибка осталась бы незамеченной до первой морозной ночи.

Верните исходную строку и убедитесь, что все тесты снова проходят.

## Чего тесты не проверяют

Заглушка подтверждает, что драйвер ведёт себя так, как мы его понимаем. Она не подтверждает, что мы правильно поняли датчик. Если в datasheet прочитан не тот номер регистра, неверный будет и код, и тест, и они будут согласованно проходить.

Поэтому ожидаемые значения нужно брать из документа, а не из головы. Остальное проверяется только на реальном железе: подтяжки шины, тайминги, реальные значения датчика. Для этого в плане есть отдельная глава.

## Упражнения

Выполняйте их в таком порядке. Каждое лучше начинать с теста, а затем писать код, чтобы тест пройти.

**1. Чтение конфигурации.** Добавьте метод `read_configuration`, который возвращает регистр конфигурации как `u8`. Подсказка: он повторяет первую половину `modify_configuration`.

**2. Проверка адреса.** Добавьте `Address::from_bits(bits: u8) -> Option<Address>`, который принимает только значения от `0x48` до `0x4F`. Проверьте границы: `0x47` и `0x50` должны давать `None`.

**3. Порог перегрева.** Регистры Tos (`0x03`) и Thyst (`0x02`) хранят 9-битное знаковое число в битах с 15-го по 7-й, шаг равен 0,5 °C. Добавьте метод `set_overtemp_threshold`, который принимает температуру в полуградусах (`i16`) и записывает её в Tos. Чтобы получить значение для записи, нужно сдвинуть число влево на 7 бит. Проверьте положительное и отрицательное значения. Для записи в такой регистр нужно отправить три байта: номер регистра и два байта данных.

**4. Намеренный сбой.** Измените адрес в одном из тестов, например `0x4D` на `0x4C`, и прочитайте сообщение заглушки. Полезно знать, как выглядит диагностика, до того как она потребуется по-настоящему.
